## 字幕断行与视觉规则（2026-09-09 确认）

断行规则依据本机 AI剪口播 技能：`C:\Users\NBAMA\.codex\skills\AI剪口播\用户习惯\断行prompt.md`。

- 每行 ≤16 字；能单行完整就不拆。
- 断点优先级：句子/从句自然边界 > 连词前（但是、所以、因为、然后、而且）> 话题转折处（其实、另外）> 动词前（主语留上行，谓语下行）。
- 同一行内不拆：动宾搭配、偏正短语、介词短语、数量词+名词、专有名词、“的”字结构。
- 两行不等时下行更长（梯形），避免上行只有两三字。
- 字幕文本去掉中英文标点（保留 GPT-4 这类英文连字符）；中英/中数之间不加空格，英文单词之间保留空格。
- 断行是 AI 语义处理，不能用纯字符/词级切分代替；由编排 agent 逐条口播稿处理，再按转写段落回填时间轴。
- 字幕不做关键词黄色高亮：`caption_emphasis` 填 `["__none__"]` 关闭自动提取。
- IP 介绍：横屏整段常驻；竖屏只在 2–6 秒出现（founder 模板已按画幅条件实现）。
- 封面默认出 16:9 与 3:4 两版；账号子文件夹提供单独人像照片时，3:4 改用 gpt-image-2 图生图（提示词模板 `cover-prompt-photography.md`，标题取该视频），16:9 仍用抽帧 + 标题模板。

## 一话题多账号：文案必须各不相同；跨平台则可以共用一套（2026-09-18 口径更新）

**两条要分开看，别混成一条：**

1. **同一个视频发到不同平台 → 可以用同一套文案**，只按平台规则做微调（标题字数上限、标签写法、该平台是否支持 tags 字段、平台语气），不必从零重写。微调的边界：事实、主关键词、案例与数字必须保持一致，只动表达与格式。
2. **同一个主题的不同视频、发到同一平台的不同账号 → 标题、正文、标签必须各不相同**，不能共用一套。

同一条口播会录 大号 / 小号1 / 小号2 / 企业号 多个机位（有的批次只有其中几个）。**跨账号必须分别写**：

- 片内话题锁（`topic_line_1` 三段 + `topic_line_2`）每个账号都不同；
- 强调词（`cover_emphasis`）跟着封面标题走；

## 本机发布的失败排查与重试（2026-09-13 实测）

本机发布常见三类失败，处置方式不同：

| 报错 | 阶段 | 处置 |
| --- | --- | --- |
| `视频下载失败:<OSS URL>` | `upload/fail` | 平台侧抓不到蚁小二 OSS 上的文件。**先用 `ffmpeg -c copy -movflags +faststart` 重新封装成片**（内容哈希变了就会生成新的 OSS 对象），再重发；若换对象仍失败，转去检查该账号在客户端的授权状态 |
| `登录失效` / `获取用户信息失败登录失效` | `push/fail` | 账号在蚁小二客户端里的授权过期——需要用户重新登录/授权该账号，然后重发（重新授权后同一账号此前失败的抖音任务往往也一并恢复） |
| `ENOENT ... platform-service\\video\\*.mp4` | `push/fail` | 客户端本地下载中断，直接重发即可 |

重试纪律：

- 发布脚本必须按 **(素材, 平台)** 记录状态，重试只补失败项，已成功的自动跳过，绝不重复发布；
- 每次重试后都要用 `yxer query records` + `query details` 回查平台侧真实状态（`stageStatus=success` 且 `errorMessage` 为空才算成功），不能只看 CLI 返回的 OK；
- 抖音的成功率明显低于其他平台（2026-09-13 实测 33 个任务里首轮失败 8 个抖音），批量发布后要留一轮重试。

## 素材下载必须直连，不要挂代理（2026-09-15 实测）

本机发布的素材要先从蚁小二 OSS（`https://oss-v2.yixiaoer.cn/yfb/...`）下载到本机，再上传到目标平台。这段下载**不要走代理**，尤其不要在蚁小二账号里绑代理节点。

| 路径 | 结果 |
| --- | --- |
| 直连（推荐） | 179.9MB / 6.5 秒 / 27.8MB/s，一次下完 |

## 卡在 `upload/doing` 的任务不会自愈（2026-09-15 实测）

- 客户端是**事件驱动**：云端推一条 `task:push`，客户端处理一条。**推送时没跑成功的任务不会再自动重试**，会永久停在 `upload/doing`。
- **重启客户端无效**（不会重新推送）；在客户端点「重新发布」有效（等于云端重新推送）；重新提交一份同样的任务也会被处理，但会多出一条记录。
- `yxer publish` 只有 `delete` / `form` / `init` 三个子命令，**没有 retry 接口**，无法用 CLI 触发重推。
- `upload/doing` 的任务**删不掉**：`yxer publish delete <task_id>` 返回 `403 任务不是发布状态，无法删除`；客户端 app.asar 里也没有删除任务的入口。这批任务是惰性的，不会自己变成已发布，只是占着队列。
- 所以**换代理节点 / 关代理 / 修好网络之后，必须回头处理积压**：要么在客户端逐条点「重新发布」，要么按下一条重建。

## 积压任务的重建办法（2026-09-15 实测）

卡住的任务既删不掉也推不动时，**拿本地原始 payload 重发一份**，把 `scheduledTime` 填回原来的时间点即可。客户端收到新任务会立刻上传到平台，再由平台侧定时发布。

重建前的三个必查项：

1. **按平台索引 payload**。同一素材的多平台 payload 共用封面/视频 key，只用 key 匹配会把抖音的任务对到小红书的 payload 上，必须用 (平台, key) 联合匹配。
2. **核对 `platformAccountId` 是否还有效**。账号重新授权后 ID 会变，旧 ID 提交会被拒；用 `yxer accounts list` 对照当前账号 ID。
3. **已有成功副本的一律跳过**。同一账号 + 同一时间点 + 同一内容只要存在 `stageStatus=success` 的任务，就绝不再重发。

重建命令仍是同一套本机通道：`yxer validate <平台> video <payload> --publish-channel local --client-id <id>` → `yxer publish video <平台> <payload> --dry-run ...` → `yxer publish video <平台> <payload> ...`。

## 批量提交必须串行限流（2026-09-15 实测）

**一次把几十上百条任务灌给客户端，会失败一大半。** 客户端收到推送后是并发上传的，一条成片约 180MB，同时开工就把带宽吃满，单条上传被拖过 200 秒超时：

```
timeout of 200000ms exceeded
```

当天实测：一次性提交 98 条（小红书 37 + 抖音 36 + 视频号 26），只有 12 条成功、86 条超时失败；同一天单条提交的（08:15 / 08:23 / 08:44 各一条）全部成功。改成**串行**——提交一条、轮询到它不再是 `doing`、再提交下一条——之后连续 50 多条零失败。

所以批量发布脚本必须做成串行队列，不要 for 循环一次性提交：

1. 提交 `publish`；
2. 轮询这条任务的状态（每 20 秒左右查一次，只扫最新几条记录，别整库扫，会拖慢流水线）；
3. 等到它不再是 `doing`（或超时）再提交下一条。

单条从提交到出结果约 1–2 分钟，100 条约 2 小时，排期时要留够时间。

## 判断「是否已发布」要看 publishId，不能只看 stageStatus（2026-09-15 实测）

`stageStatus` 为 `fail` 的任务**不一定没发出去**。实测 11 条 `review/fail` 的抖音任务全部带有 `publishId`——作品已经推给平台了，只是蚁小二没取到平台的审核状态。把这些当成失败重发，直接产生了重复作品（当天误发 7 条，事后用 `yxer publish delete` 撤掉）。

正确口径：

- **有 `publishId` 就算已经交给平台**，一律不再重发；
- `review/doing`、`scheduled/success`、`push/success`、`success/success` 都算在途或已完成；
- 只有既没有 `publishId`、状态又是 `fail` 的，才是真失败。

重建 / 补发脚本开工前必须先按这个口径扫一遍现状，把已发出的剔掉，再补剩下的。

## 超时阈值按平台不同，30 秒 = YouTube 云发布（2026-09-18 实测）

同一套流水线里，超时阈值按**发布通道**分成两档，看报错里的毫秒数就能判断是哪一档：

| 阈值 | 平台 | 通道 | 含义 |
| --- | --- | --- | --- |
| `timeout of 200000ms exceeded` | 抖音 / 小红书 / 视频号 / 快手 / B站 | 本机发布 | 客户端本地并发上传，被带宽拖过 200 秒 |
| `timeout of 30000ms exceeded` | **YouTube** | **云发布** | 云端接管上传，本机只是在**轮询状态**，30 秒拿不到结果就判失败 |

YouTube 走云发布，本机 `platform-service` 日志里**完全没有 YouTube 记录**（视频号/抖音/小红书都在）。

**为什么 YouTube 不能走本机通道（2026-09-18 查证客户端代码）**：蚁小二客户端本机只实现「浏览器会话发布」——
用内置 Chromium 打开各平台创作后台（`channels.weixin.qq.com`、creator.douyin.com、creator.xiaohongshu.com 等）完成上传，
所以这些平台的痕迹都在本机 `platform-service` 日志与 `Partitions/auth-*` 会话目录里。
YouTube 没有网页创作后台、走的是 Data API + OAuth，客户端本机**没有对应实现**：
在 `D:\Program Files\yixiaoer\resources\app.asar` 里按平台名计数，
`shipinhao` 52 / `xiaohongshu` 43 / `douyin` 38 / `bilibili` 17，而 **`youtube` 只有 3 处，且全部是 `mime-db` 的 MIME 类型字符串**（`video/vnd.youtube.yt`），没有任何发布逻辑。
即：**YouTube 只能走云发布，不是可切换的选项**；那个 30 秒超时是云通道固定的等待窗口，客户端里没有可调开关。

上传一条 200–285MB 成片要几分钟，远超 30 秒轮询窗口，于是：

1. 本机把这条标成 `upload/fail` + `timeout of 30000ms exceeded`；
2. **但云端上传仍在继续，视频最终是发出去的**；
3. 流水线按「fail 就重发」处理 → 重试时第一条已上传完成 → **YouTube 里出现两个副本**。

**2026-09-18 实测代价**：0903 批次 6 条 YouTube 内容，每条都被重发一次，账号里出现 12 个条目（用户 YouTube Studio 截图确认），
观看量被拆成两份（例如同一条印度客户视频：150 观看 + 3 观看）。

处理规则：

- **看到 `30000ms exceeded` 一律先当成「可能已发布」**，不要立刻重发。
- 判定要**等一个冷却期**（建议 ≥10 分钟）再去平台后台核对；YouTube 没有查询接口，**只能人工看 YouTube Studio**。
- 只有「无 `publishId` + 状态 `fail` + 平台后台也确实没有」，才是真失败。
- 补发 YouTube 前，先在 Studio 里按**标题 + 时长**核对（时长是最可靠的指纹，各条互不重复；仅看标题容易把重复副本当成已发）。
- **YouTube 无法改成本机发布**（客户端没有该实现，见上）。要彻底避免重复，二选一：
  ① 交给蚁小二云发布时，**提交后不要立刻判定失败**——记下 taskId，隔 30 分钟以上再去 YouTube Studio 核对，确认没有再补发；
  ② 大文件（≥150MB）干脆**手动在 YouTube Studio 上传**，绕开 30 秒窗口。
- **2026-09-20 用户确认：本轮 0919 批次的 10 条 YouTube（全部拿到 `openUrl`）与 2 条哔哩哔哩 `notfound`（有 `publishId`）都不用再管**，不需要人工去 Studio / 创作中心核对，也不再列为待办。**注意这只针对本轮**：以后新批次仍按上面的冷却期规则处理。

## 视频号短标题（2026-09-20 用户要求）

- 品牌一律用业界通用缩写：`WA`（不写 WhatsApp）、`FB`（不写 Facebook 全称）、`IG`/`Ins`（不写 Instagram 全称）；
- 不写翻墙/规避类工具名；
- 不写「必火、稳赚、百分百」这类绝对承诺；
- 不写原稿没有支持的客户数据或收益数字。

**交稿前必须逐条通读标题、正文、标签**，命中违禁词直接改写，不要指望平台「也许不查」。这条优先级高于下面所有写作风格要求。

**适用范围：所有平台，不是只给小红书。** 小红书 / 抖音 / 视频号 / B站 / 快手 / YouTube 等所有要发布的封面文字、标题、正文、标签，一律按下面的规格来写——事实纪律、六大因子、关键词四维、输出规格、三策略与筛选顺序，一个都不省。

唯一的例外是平台自身的硬限制（标题字数上限、标签数量上限、不支持标签等）：**平台限制与本规格冲突时取更严的那一条**，并在交付说明里写清是哪个平台、卡在哪条限制上。不要因为「换个平台」就退回不带因子、不做关键词、不核字数的写法。

本节与「活人感写作」「一话题多账号文案各不相同」叠加使用：先按本节写，再过活人感写作去 AI 腔。**跨账号**（同一主题的不同视频发到不同账号）时每个账号各跑一遍；**同一个视频跨平台**时可以共用一套，只按平台规则微调。

### 事实纪律（先于润色）

- 案例、数据、身份、来源（即「他证」）只能取口播原稿里明确给过的；人设只能用用户已给的经历。
- 不编造案例、数据、政策、地点、收益；推测不写成定论；历史年份不机械替换成今年。
- 不写「必火 / 稳赚 / 百分百 / 淘汰」这类绝对结论；情绪词服务于事实。
- 保留作者观点和语气，删掉口头重复。

### 标题六大因子

先给标题做因子标注，再挑最有力的 3–4 个组合（不要堆满六个）：

| 因子 | 作用 | 可用表达 |
| --- | --- | --- |
| 数字 | 降低理解成本、制造清单预期 | 3 个方法、60 天、只做 1 件事 |
| 痛点/爽点 | 先说损失或想要的结果 | 没流量、总被拒、效率翻倍 |
| 人群 | 让目标读者对号入座 | 新手博主、外贸老板、工厂老板 |
| 他证 | 提供可信来源或案例 | 实测、客户案例、行业报告 |
| 情绪 | 增加紧迫、好奇或共鸣 | 别再踩坑、终于、低估了 |
| 人设 | 说明作者为何值得听 | 8 年实操、从 0 做到 X |

参考句式：`数字 + 人群 + 痛点：结果/方法`、`人群 + 痛点？用 X 解决`、`他证/人设 + 爽点：我如何做到`、`情绪提醒 + 核心关键词 + 具体场景`。

### 关键词四维

| 维度 | 提取问题 | 示例 |
| --- | --- | --- |
| 人群 | 谁需要这条内容 | 新手博主、外贸老板 |
| 痛点 | 正在搜索什么困难 | 笔记没流量、询盘少 |
| 爽点 | 想获得什么具体改善 | 找到选题、省时间 |
| 地点 | 需求是否受地域影响 | 深圳装修、杭州探店 |

每稿提取 **1 个主关键词 + 3–5 个关联词 + 5–8 个长尾短语**。长尾是指意图更具体，不是凑字数：`人群+问题`、`对象+怎么做`、`场景+方法`。地点只在本地服务、线下消费或地域确实影响答案时才用，否则标「无地域需求」，不虚构城市，也不把平台名当地点；爽点必须有原稿支撑。

没有搜索工具时照样出稿，但要标注「关键词由原稿推导，待站内验证」，不虚构搜索量、热度或竞争度。

### 输出规格（用户要求优先；所有平台通用）

| 内容 | 数量 | 长度与要求 |
| --- | --- | --- |
| 封面文字 | 1 组 | 2–3 行，每行 4–10 字，总计 12–24 字 |
| 笔记标题 | 3 个，推荐 1 个 | 每个 16–20 字，前 10 字尽量放主关键词 |
| 发布正文 | 1 版 | 100–160 字，不含标题标签，2–4 个短段 |
| #话题标签 | 默认 10 个 | 8–12 个之间按相关性调整 |

上表对每个平台都适用：**每个平台都要交 3 个标题和 1 版正文**，不是只有小红书才要。字数按可见字符计：中文、字母、数字、标点各算 1，忽略空格和换行。输出前核对长度，不凭感觉报精确数字；少用 emoji。某个平台标题上限短于 16 字时，按该平台上限定稿，但保留主关键词在前 10 字的位置要求。

### 三个标题策略与筛选顺序

1. **搜索型**：主关键词 + 人群/场景 + 明确问题或方法，优先覆盖长尾搜索。
2. **点击型**：数字或痛点/爽点 + 情绪词 + 人群，正文要能兑现承诺。
3. **信任型**：他证或人设 + 结果 + 方法/边界，适合专业服务与经验分享。

推荐排序：**内容兑现度 > 关键词清晰度 > 读者相关性 > 新鲜感**。逐项自检：有没有至少 1 个核心关键词？前 10 字出现主题了吗？口播里找得到证据吗？有没有因果夸大？

输出标题时在括号里标因子（如「（数字＋人群＋痛点）」），**因子标签不要混进可发布的标题**。

### 正文与标签

- 正文第一句点明人群/问题并自然带出主关键词，中间给原稿里 1–3 个真实要点，结尾可补视频价值或相关问题。标题和正文开头各自然出现一次主关键词即可，不设关键词密度指标。
- 标签默认 10 个，分配：**主题 2 + 人群 2 + 痛点 2 + 结果 2 + 细分场景/相关业务 2**；有地域需求时从最后一类替换 1–2 个。标签以 `#` 开头、内部不留空格、之间用空格分隔，不重复、不凑数。**每个平台都要按这套分配写标签**（平台不支持标签的除外，如 YouTube 用 Tags 字段，但数量和维度分配不变）。
- **与「一话题多账号文案各不相同」叠加**：**同一个主题的不同视频发到不同账号时**，主关键词可以相同，但标题、正文和 10 个标签必须按账号定位换角度重写，不能把一个账号的文案直接搬到另一个账号用。**同一个视频发到不同平台时不受此限**——可以共用一套文案，只按平台规则微调（2026-09-18 用户口径）。
- 交付顺序：先给可直接复制的封面文字、3 个标题、正文、整行标签；字数与标签数量写在发布文本之外。用户要分析时再补四维拆解、主词与关联词、5–8 个长尾词、优先覆盖的 2–3 个词及原因、验证状态。

## 生图封面（2026-09-10 已验证）

- 适用范围：账号子文件夹提供单独人像照片时，**只用于 3:4 封面**；16:9 封面继续用 KB Cut 抽帧 + 标题模板，不调用生图。
- Base URL：`https://jojocode.com`（`.env` 的 `JOJOCODE_BASE_URL`）。
- 模型：`gpt-image-2`（`.env` 的 `JOJOCODE_MODEL`）。
- 接口：`POST {BASE_URL}/v1/images/edits`，multipart 图生图；可用 `GET /v1/models` 自检。
- 鉴权：`Authorization: Bearer $JOJOCODE_API_KEY`，密钥只从编排目录 `.env` 读取，不回显、不提交。
- 提示词模板：[cover-prompt-photography.md](cover-prompt-photography.md)。标题两行替换为该视频自己的封面标题（如 082610 用「八年设计 / 转外贸」），字数标注同步改成实际字数，其余逐字保留。
- 参数：`size=1080x1440`（接口返回 1088x1440，交付前用 ffmpeg 缩到 1080x1440）、`quality=high`、`input_fidelity=high`、`n=1`。
- 调用方式：Windows 用系统 `curl.exe`（Python urllib 会因证书链报 `CERTIFICATE_VERIFY_FAILED`）；提示词用 UTF-8 文件传参 `-F "prompt=<prompt.txt"`，避免命令行编码问题：

```powershell
curl.exe -sS -X POST "$base/v1/images/edits" `
  -H "Authorization: Bearer $key" `
  -F "model=$model" -F "prompt=<$promptFile" `
  -F "size=1080x1440" -F "quality=high" -F "input_fidelity=high" `
  -F "image=@$photo;type=image/png" -o result.json
```

- 生成图已含标题文字，直接作为 3:4 封面交付；不要再叠加封面模板标题。
- 2026-09-10 验证记录：`GET /v1/models` 返回 `gpt-image-2` 与 `gpt-image-2-4k`；`/v1/images/edits` 接受 `size=1080x1440`、`quality=high`、`input_fidelity=high`。
