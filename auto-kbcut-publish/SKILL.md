# 自动剪辑发布编排

把「KB Cut 剪辑 → 活人感写作 → 生图封面 → 蚁小二发布」串成一条由“开始剪辑”触发的编排流程。本技能只负责编排、门禁和状态回写，不替代 kbcut、human-writing、yixiaoer 技能各自的内部逻辑。

## 触发与模式

- `开始剪辑`：全自动。
- `开始剪辑 半自动`：半自动。
- `开始剪辑 大号` / `开始剪辑 小号` / `开始剪辑 企业号`：只处理指定账号子文件夹，默认全自动。

### 两种模式的分界（2026-09-17 用户再次确认）

**全自动（`开始剪辑`）**：从检测素材文件夹开始，到剪辑、渲染、封面、文案、排期、提交发布，**全程不向用户提问、不等待确认**。遇到可选方案自己按既定规则拍板（风格 founder-interview、画幅按素材长宽比、钩子保留原开头、裁切居中、IP 老秦），做完直接把结果汇报。只有真正阻塞（素材损坏、平台拒绝、客户端离线）才停下来报告。

**半自动（`开始剪辑 半自动`）**：在全自动基础上**只多两个暂停检查节点**，其余环节同样不问：

1. **节点一 · 封面与截图检查**：本批所有视频出好封面（16:9 + 3:4）与带字幕截图（每条 4 张，按成片时长取点）后停一次，一次性交用户看；用户点头才继续整片渲染。
2. **节点二 · 发布前总检查**：整片渲染完成、文案（标题 + 正文 + 标签）写完、payload 组装好后，**提交发布之前**停一次，把成片与文案交给用户确认；用户点头才提交。

除这两个节点外，半自动与全自动完全一致——中间过程不问（不逐条确认、不中途问风格、不问要不要改文案）。

开始前先读 [references/config.md](references/config.md) 获取路径、映射、默认参数、排期与密钥来源，并读取编排目录 `.env` 中的 `JOJOCODE_*`（只读入环境，不回显、不打印密钥）。

## 执行流程

1. 扫描素材根目录 `G:\0 视频未剪辑`，只处理「日期命名且包含两个及以上账号子文件夹」的日期文件夹。
2. 用 `processed.json` 做增量：只处理新增或变化的视频，跳过已处理且未变化的文件。
3. 对每条新视频执行 KB Cut：
   - 全自动：跳过交互门，直接写入 `input_choices.json`。风格 founder-interview；画幅按素材长宽比（竖屏 9:16、横屏 16:9）；**3 秒钩子=保留拍摄时的原始开头顺序，不寻找、不前置金句**（`hook_strategy: preserve_original_opening`、`hook_reorder_authorized: false`）；裁切=居中/自动；个人 IP=老秦。
   - 半自动：画幅仍按长宽比自动，但先确认风格、3 秒钩子策略、裁切锚点（复用 KB Cut 裁切对比图）。
   - 字幕：口播优化版复核转写后，按「AI剪口播 断行规则」（references/config.md 有完整版）做 AI 语义断行：每行 ≤16 字、一句一段、去标点、不拆动宾/偏正/介宾/数量词+名词/专名/“的”字结构，生成的字幕 SRT 再进包装；不要用纯字符切分。
4. KB Cut 转写完成后，**每个平台都**先按 `xhs-copy-keyword-mining` 的规格（事实纪律、六大因子、关键词四维、封面 12–24 字 / 标题 3 个×16–20 字 / 正文 100–160 字 / 标签 10 个）起草封面文字、标题、正文与标签，再交给 human-writing 做「活人感」润色，生成发布物料，覆盖 KB Cut 默认文案。适用于小红书 / 抖音 / 视频号 / B站 / 快手 / YouTube 全部平台，不是只做小红书；平台自身限制更严时取更严的那条。
5. 封面：账号子文件夹里有单独人物照片（png/jpg/heic）时，3:4 封面用 gpt-image-2 图生图（提示词模板见 [references/cover-prompt-photography.md](references/cover-prompt-photography.md)，两行标题替换为该视频自己的封面标题，生成图已含标题，直接交付）；16:9 封面仍用 KB Cut 抽帧 + 标题模板，不做生图。没有照片时两版都用 KB Cut 默认封面。
6. 预览（每条 6 张图：2 个封面 + 4 张带字幕截图，按成片实际时长取点）：**半自动**在这里停一次，一次性交用户确认后才统一批量渲染（不要逐条确认逐条渲染）；**全自动**照常产出这些预览图并归档到 `工作文件/预览截图/`，但**不等待确认**，直接继续渲染。
7. 按账号子文件夹映射蚁小二账号组，用 yxer 上传视频和封面、组装 payload、`validate` → `publish --dry-run` → 正式发布；定时发布用 `scheduledTime`，时间取 config.md 的非整点排期。
8. 发布后必须回查任务状态（`yxer query records` / `yxer query details`）：
   - 全部成功 → 用 ✅ 汇报，并把该视频在 `processed.json` 标记为 `published`。
   - 任一平台失败 → 用 ❌️ 逐条提醒用户：平台、账号、错误信息、任务 ID；失败视频**不要**标记为已发布，保留可重试状态，修复或确认前不重复正式发布。
9. 回写 `processed.json`，输出本轮的剪辑与发布汇总。

## 硬约束

- 素材目录只读：不在 `G:\0 视频未剪辑` 内写文件或建项目。
- 状态文件 `processed.json` 与 `.env` 都放在编排目录 `C:\Users\NBAMA\Documents\自动剪辑`。
- 生图密钥只从 `.env` 读取，不写入文档、不回显、不提交。
- 文案按 `xhs-copy-keyword-mining` 的规格写（事实纪律、标题六大因子、关键词四维、封面 12–24 字 / 标题 3 个×16–20 字 / 正文 100–160 字 / 标签 10 个），再用 human-writing 去 AI 腔。**这条对小红书 / 抖音 / 视频号 / B站 / 快手 / YouTube 所有平台一视同仁**，不是只做小红书；平台自身限制更严时取更严的那条。同一话题下每个账号、每个平台的标题与标签必须各自重写，不能共用一套。细则见 [references/config.md](references/config.md) 的「标题与文案规格」。
- 发布必须先用同一份 payload 和同一套发布通道参数完成 `yxer validate` 与 `yxer publish --dry-run`，通过后再正式发布。
- 发布通道**一律本机发布**（`--publish-channel local --client-id Z-jzdLWSjV1Zmo6hTXpD9`），不用云发布；本机的网络**不要挂代理**（含蚁小二账号里的代理节点）——素材要从蚁小二 OSS 下载，走代理会中途断流并把任务卡死在 `upload/doing`。
- 定时发布同样走本机提交（带 `scheduledTime` 也用 local，不必改用云通道）。**硬条件只有一个：提交 `publish` 那一刻蚁小二客户端必须在运行**——客户端关闭时 `publish` 会返回「检测客户端设备未连接,请稍后再试」，而 `validate` / `--dry-run` 仍会通过，不能拿它们判断环境就绪。提交前先确认客户端进程在，不在就先启动 `D:\Program Files\yixiaoer\蚁小二4.0.exe`。**到点那一刻本机不必在线**：客户端在提交时就完成「拉素材 → 上传平台 → 设置平台侧定时」，之后交给平台。
- 代理变更（换节点 / 关代理 / 修网络）之后**必须回头重推积压**：卡在 `upload/doing` 的任务不会自愈，重启客户端也没用，只能在客户端点「重新发布」，或用本地原始 payload 重建任务。
- **批量提交必须串行**：一条提交完、轮询到它不再是 `doing`，再提交下一条。一次性灌几十上百条会让客户端并发上传把带宽打满，单条被拖过 200 秒超时（`timeout of 200000ms exceeded`）——2026-09-15 实测一次提交 98 条，86 条超时失败；改串行后连续 50 多条零失败。
- **判断「是否已发布」要看 `publishId`**：`review/fail` 这类状态不代表没发出去（实测 11 条都已有 publishId，作品已在平台）。有 publishId 就绝不重发，否则会产生重复作品。
- 平台定时下限：抖音至少提前 2 小时，快手至少提前 1 小时；过点内容必须顺延，不能原时长重发。
- 快手 / 哔哩哔哩 不吃平台侧定时，本机提交即发布；给它们排期只能在目标时间点现场提交。
- `scheduledTime` 不得用整点（X:00），按 config.md 的非整点排期表。
- 半自动的两个暂停点：①封面 + 截图检查（渲染前）；②成品 + 文案检查（提交发布前）。**除这两处外不再打断用户**。
- 整片渲染前必须先出齐**批次级**预览（每条 2 封面 + 4 截图，按成片时长取点）。半自动在此等待用户一次确认后才批量 `hyperframes render`；全自动直接继续，不等待。
- 渲染与压缩走 GPU：整片 `hyperframes render` 必须带 `--gpu`；成片压缩用 `h264_nvenc -preset p5 -tune hq -rc vbr -cq 19 -b:v 8M -maxrate 8M -bufsize 12M`，无 NVENC 时回退 `libx264 -crf 20 -preset medium`。中间文件（口播优化版）用 `h264_nvenc`/`hevc_nvenc -rc vbr -cq 26 -b:v 0`——实测该档与旧默认 `libx264 crf20` 码率持平（2.46 vs 2.41 Mbps）且 SSIM 略优（0.9829 vs 0.9818）；NVENC 的 cq 比 x264 的 crf 松，不要照搬 crf 数值。实测 60 秒 1080p 素材：`libx264` 压缩耗 CPU 105.6s，`h264_nvenc` 仅 2s；3 并发时差距更大。GPU 不可用时自动回退 CPU，画质参数不变。
- 字幕行 ≤16 字、一句一段、AI 语义断行，不做关键词黄色高亮（`caption_emphasis` 用 `["__none__"]` 关闭自动提取）。
- IP 介绍：横屏整段常驻；竖屏只在 2–6 秒显示。
- 封面默认出 16:9 与 3:4 两版。账号子文件夹有单独人像照片时：3:4 用 gpt-image-2 图生图（`references/cover-prompt-photography.md` 模板，标题取该视频封面标题的两行文字），16:9 仍用 KB Cut 抽帧 + 标题模板；没有照片时两版都走 KB Cut 默认封面。
- 发布不是“提交成功就算成功”：CLI 返回任务 ID 后必须回查记录；失败一律用 ❌️ 明确提醒用户，成功用 ✅。
- **收尾必须过「交付前全量核对」清单**（见 [references/config.md](references/config.md) 同名章节）：画面 / 文案 / 成片与文件 / 发布四大类逐条核对，**去看实际产物而不是凭记忆**，核对结果写进汇报；任一条没做到先补做，不许直接报「已完成」。用户已多次指出「前面提过的要求被忘掉」，这一步是强制门。
- **文案必须先过 `$human-writing`（活人感写作）才能进交付文件、才能提交发布**：顺序是「按 xhs-copy-keyword-mining 起草 → 过 human-writing → 红线自查 → 落盘」。禁止把起草稿直接当成品交付。2026-09-17 用户发现发布的文案跳过了这一步，已重写并补记。
- **发布提交成功后必须删掉该条项目的整个 `工作文件/`**（2026-09-17 用户新增规则）：只要该条视频的**所有目标平台任务都提交成功**（拿到 `publishId`，即时发布与定时发布都算），就把 `<项目>/工作文件/` 整个删除，只保留 `交付文件/`。**只要有任一条没提交成功，就先留着 `工作文件/`**，补齐后再删——失败排查还要用它。
  - 代价要说清：`工作文件/` 里有口播优化版、转写、`edit_plan.json`、`input_choices.json` 和 hyperframes 打包目录，删掉之后**想重渲染就得从 G 盘原素材重跑一遍转写与剪辑**。这是用户明确选择的取舍，正常执行即可，但删之前要确认这一条的成品已在 `交付文件/` 里且校验通过。
- **「交付前全量核对」在两种模式下都必须执行**（2026-09-17 用户强调）：全自动 ≠ 不核对，全自动是「不向用户提问」，核对是**自己的强制自检**，在提交发布之前静默跑完，把核对结果写进汇报；半自动则在**节点二（提交发布前）之前**跑完。**没跑过核对门就不许提交发布，也不许汇报「完成」**。核对的依据是用户在本任务和历史上提出过的全部要求——逐条去看实际产物（文件尺寸、目录名、文案文本、发布记录、清理状态），不是凭记忆答。
